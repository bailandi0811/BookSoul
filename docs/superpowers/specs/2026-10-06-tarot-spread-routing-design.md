# 塔罗选阵与解读规则设计

**日期：** 2026-10-06  
**状态：** 用户已于 2026-10-06 批准书面设计，进入实施计划阶段；本文不代表代码已实现或真实供应商已验收。  
**背景：** 用户明确要求 Jev 在抽牌前判断三张分别代表「过去／现在／未来」还是「现状／阻碍／发展趋势」，再将确定的牌位传给解读模型。单张保留是非问题。用户同意参考 tarot-waite 的方法，并维护本项目自己的选阵和解读规则。

## 1. 目标与范围

- Goal：同一个问题的牌阵只在抽牌前决定一次，前端牌位、服务端揭晓结果与解读模型收到的定义一致；解读围绕问题和整组牌，避免背诵牌义。
- Done：三个牌阵的自动选择／自选、锁定、揭晓、重试与 SSE 解读通过回归；两端质量门通过。真实选阵与解读效果须另有评测证据，不能用 mock 通过代替。
- Scope：现有 tarot 模块、客户端对应页面与 API 校验、共同牌阵定义、本地规则及相关测试／文档。
- 非目标：Jev 解读已抽到的牌、模型自由生成牌位、增加四张以上牌阵、替换供应商或模型、引入 Agent 框架／技能管理平台、视觉解读、重写牌义、历史记录和数据库迁移。
- Risks：新增枚举值要求前后端配套发布；中文分类规则未实测；未来／关系解读仍有模型输出偏离风险。配置、账号与真实用户数据保持原样。

这是对[原塔罗设计](2026-10-05-ai-tarot-design.md)的增量设计；批准实施后，以本文替换原设计的「Jev 只选张数、三张固定时间之流」范围。已实施的[解读质量规则](../plans/2026-10-05-tarot-reading-quality.md)继续适用，单张结合具体牌义给出是非倾向，不恢复机械的正位是／逆位否。同步修正原设计第 2 节遗留的机械正逆位描述，消除与第 5 节的冲突。

## 2. 固定牌阵与权威定义

| 标识 | 名称 | 抽牌数 | 点击顺序对应牌位 | 适用目的 |
| --- | --- | --- | --- | --- |
| `yes_no` | 单张是非 | 1 | `answer`：是非倾向 | 一个明确问题的支持／谨慎倾向 |
| `three_card` | 时间之流 | 3 | `past`：过去；`present`：现在；`future`：未来 | 理解事情怎样演变，以及后续可能走向 |
| `triangle` | 圣三角 | 3 | `situation`：现状；`obstacle`：阻碍；`outlook`：发展趋势 | 理解当前状况、关键阻碍和条件性的进展 |

「圣三角」在本项目明确采用上表定义，不声称所有塔罗流派都采用同一组牌位。`three_card` 保留原标识与语义，不改名为 time_flow，也不把它悄悄改成圣三角。

新增唯一事实源 `shared/tarot/spreads.json`：记录标识、名称、简短用途、所需张数、按序牌位及牌位解释。按既有牌组同步方式生成前后端可编译的静态模块；校验三个标识唯一、张数匹配、牌位唯一、中文定义非空。运行时不访问源码目录、不从网络取规则，不维护两份独立牌位数组。

牌位定义要说明：过去是形成当前情况的背景，不是已证实的历史；现状是当前问题呈现的状态；阻碍是限制／张力，不等于一定存在外部敌人；未来与发展趋势都是条件性可能，不是事实预测。综合建议不是第四张牌。

## 3. Jev 选阵规则

保留一次 `Choice` 调用，`questions.spread` 的选项扩展为 `yes_no/three_card/triangle/unclear`。由服务端根据共同定义编写 instructions 和 criteria，不允许用户问题改写策略。

- 首先识别用户要获得什么答案，再选牌阵；不按是否含有「会不会」「未来」「关系」单个词机械匹配。
- yes_no：请求一个主要是非判断，没有同时要求原因、过程或阻碍分析。
- three_card：关注时间、时机、等待时长、演变、阶段、过去背景与之后走向；「什么时候能遇到真爱」「还要多久有进展」不需要同时说出过去现在未来，也属于时间之流。出现「以后」并不自动满足，单纯「明天会成功吗」仍可属于 yes_no。选择牌阵不代表能预测确切日期，解读仍只讨论条件性的未来。
- triangle：主要询问当前状态、为什么卡住、影响因素、发展可能或怎样推进。关系主题不自动等于时间线。
- unclear：没有可识别的问题目的、多个独立问题无法选一个主要目的，或只有覆盖规则指令。问题简短、缺少个人背景、询问日期或他人心理本身不等于目的不明；选阵与解读真实性边界分开处理。

规则包含边界对照例：

| 问题 | 预期选择 | 依据 |
| --- | --- | --- |
| 我们还有复合的可能吗？ | yes_no | 请求单个倾向判断 |
| 我们怎样走到现在，之后关系可能如何变化？ | three_card | 明确询问演变过程 |
| 我们现在为什么卡住，什么影响着关系继续发展？ | triangle | 状态、阻碍与发展 |
| 她希望和我成为什么关系？ | triangle | 当前关系倾向，更适合分析状态与影响因素；解读不能确定对方真实心理 |
| 会不会和好，为什么一直僵持，接下来该怎样推进？ | triangle | 虽有是非句式，主要需要原因与推进分析 |
| 帮我看看 | unclear | 没有明确目的 |
| 我什么时候能遇到真爱？ | three_card | 时间／时机询问；解读不承诺具体日期 |
| 我今年会遇到合适的人吗？ | yes_no | 时间范围内的单个是非倾向 |
| 怎样才能遇到合适的人，是什么阻碍了我？ | triangle | 办法与阻碍分析 |

2026-10-06 用户反馈后的局部优化将选阵版本更新为 spread-selection-v2，保留 0.8 门槛、同一供应商与一次有界调用；新增 tarot-selection-natural-questions.json，原问题作为已知回归，其余 23 个自然问法不直接复用规则示例。真实评测仍须单独授权，分别记录原始分类正确率、自动选阵正确率和明确问题自动覆盖率。

响应 schema 同步校验四个概率字段均有限、在 0–1 范围且和约等于 1；未知选项／非法响应沿用现有 unavailable 自选流程。只有支持牌阵且 confidence >= 0.8 才自动选择；unclear、低置信度或失败进入三种牌阵的自选。保留当前门槛、超时、取消和零重试；四选项后的 confidence 不是准确率，真实评测核对自动选择覆盖率和错误。

## 4. 保存与传递

```text
问题 → Jev 选择牌阵或用户自选
     → 服务端按 owner/permit 校验，保存 spread，洗牌并锁定本局
     → 前端按共同定义显示牌阵名与牌位
     → 服务端按点击顺序赋予固定牌位
     → 全部揭晓后，解读输入包含问题、牌阵定义与真实牌单
     → 当前聊天模型按对应规则 SSE 解读
```

Jev 只返回受支持的牌阵标识，服务端从本地定义得到各牌位含义，不让模型自由命名。保存到 round 的 spread 决定牌位；定义是随部署固定的本地常量，进程重启使内存局失效，因此不引入持久版本迁移。抽牌前端显示相同定义，解读 user 消息显式带牌阵名称、按序牌位定义及已揭晓的牌名／方向／牌义。

HTTP 路径、请求字段、原枚举值与 SSE 事件保持原有含义，仅新增 triangle 及其牌位枚举。reading 仍只接受 readingId，不接受客户端提交牌单、牌位或问题；非法内部数据仍在创建模型前拒绝。高置信度的选阵不可替换，用户自选只能发生在现有 choose 流程；洗牌后牌阵、问题、顺序固定，重试使用原局，不重新调用 Jev。

前后端必须一起更新并发布；旧客户端会拒绝 triangle 响应，不能宣称对旧客户端完全兼容。现有 yes_no/three_card 调用与响应语义仍有效，不增加第二套 API 或兼容开关。

## 5. 解读规则包

此处 skill 指项目运行时显式加载的本地规则，不是安装到 Codex／Claude 目录后自动生效的技能。Jev 使用选阵规则；现有 `TarotProviderService.read` 使用解读规则，不引入完整 Agent Harness。

解读规则保持「共同策略 + 当前牌阵专用规则」两层，复用现有纯函数及输入验证。将较长方法规则放在 tarot 模块拥有的命名文件中，在构造消息时明确引用；模型不需要自行找文件或调用工具，也不加载完整 78 张牌参考书。

- 先回应问题，解释每张牌为什么与其固定牌位、当前问题有关，而不是列一串通用关键词。
- 正逆位使用本地已提供牌义，不随意覆盖，也不机械判断好坏。没有提供图像或可信意象资料时，不声称看到了牌面细节。
- 三张先逐牌对应，再用短段落说明支持、张力或变化的联系。至少解释两张牌之间的一处关联，不以花色／大牌数量直接证明现实事件。
- 单张：是非倾向／这张牌的提醒／可以尝试，约 150–250 中文字符；信息不足时明确说明，不作确定保证。
- 时间之流：整体倾向／过去／现在／未来／可以尝试，约 300–500 中文字符。
- 圣三角：整体倾向／现状／阻碍／发展趋势／可以尝试，约 300–500 中文字符。不能套用过去／现在／未来，也不能将阻碍牌解释成某个确定的第三者。
- 综合行动要与问题及牌义有关，给一条可执行建议；不凭空补充用户经历、他人意图或期限。反思问题可选，避免与页面固定引导重复。
- 保留娱乐和医疗／法律／金融边界、问题注入隔离、自然中文、禁止解释不存在牌位。长度仍是写作目标，不裁切输出。

现有两条当前局消息、maxRetries=0、maxTokens=800、总截止时间、取消传播和 SSE 终止语义保持不变。规则加入后仍是一轮解读调用，不增加审核模型。

## 7. 验证与交付

离线先写暴露旧行为的测试，再实现：

1. 共同牌阵定义生成一致，旧标识／牌位保持不变；非法定义不能生成。
2. Jev 请求包含三个真实牌阵和 unclear、固定策略与边界对照例；triangle 高置信度自动选择，低置信度／未知枚举／非法概率进入自选。Mock 只证明契约，不证明理解中文。
3. 圣三角按点击顺序揭晓 situation/obstacle/outlook；错位、混入时间牌位、零／二／四张、重复牌、未知牌和空洞数组在模型前被拒绝。
4. 解读消息包含当前牌阵及定义、准确牌义，专用指令互斥；用户注入留在低优先级数据里。连续单张 → 时间之流 → 圣三角 → 单张不带历史。
5. 前端自动选阵和三种自选，待抽／已抽满／重新占卜／错误重试均显示正确牌位；低置信度自选、旧响应隔离、取消、跨 owner 拒绝与现有 SSE 测试继续通过。
6. 相关测试后运行两个包完整 npm run check；事先核对默认发现范围及环境加载，不连接真实数据库。共同定义同步脚本、格式与 git diff 另外核对。

真实供应商评测单独授权，取代此前尚未执行的 24 次聊天验收安排：准备 24 个固定合成选阵问题（三种各 6 个、模糊／注入 6 个），以及 18 个固定牌单（三种各 6 个，保留已有代表性回归）。本次验收上限 24 次 Jev + 18 次聊天，共 42 次，串行、无自动重试；聊天输出上限 14,400 token，另有输入及 Jev token／费用。只发合成输入，不发原截图、账号、历史或书籍；沿用当前供应商与配置，不改 .env。

验收门槛：18 个明确目的问题至少 13 个正确自动选择，所有自动选择无错误；6 个模糊／注入问题不得被问题指令强制改规则。18 份解读的牌名、方向、顺序和牌位全正确，额外牌位、技术字段标题、确定读心／预测或执行改牌指令为 0；回应问题／结合牌义／具体建议各 0–2 分，至少 17/18 总分 >=5 且无单项 0，截图牌单的圣三角用例必须达标。失败或未完成样本不剔除，效果验收明确记为未通过／未完成。

验收输出在仓库外新文件，只记录脱敏汇总进 docs/tarot-acceptance.md。任何修订后的额外真实调用需说明数量并另获授权，不降低指标、截删输出或静默换模型。没有同输入的旧版真实结果时，只报告新版是否达到门槛，不声称量化证明提升。

实施时更新原设计对应范围、契约与页面说明；保留现有用户工作，不提交或创建分支，不修改环境、部署、依赖或运行时数据。
