# BookSoul 聊天室成员资料实时同步设计

**日期：** 2026-10-08  
**状态：** 设计已获用户口头确认，待书面规格复核  
**相关基线：** [公共聊天室设计](2026-10-04-community-chat-design.md)、[公共聊天室交互更新设计](2026-10-05-community-chat-interaction-design.md)

本设计替换基线文档中“昵称在消息发送时保存快照，修改昵称只影响后续消息”的展示规则。消息仍保留发送时名称快照作为历史事实和故障兜底，但聊天室正常展示当前成员资料。其他未被本文明确修改的公共聊天室权限、隐私、重放、背压和数据安全约束保持不变。

## 1. 目标与完成条件

### Goal

已加入公共聊天室的用户修改名称、上传新头像或恢复默认头像并保存成功后，所有正在聊天室中的用户都通过 WebSocket 实时看到新资料，体验与接收新消息一致；错过实时事件的客户端在重连或重置恢复后得到当前资料。

### Done

- 修改者和其他在线成员无需刷新、重新登录、离开页面或等待定时轮询，即可看到更新后的名称和头像。
- 正常在线链路的端到端更新目标不超过 1.5 秒。
- 资料事件在数据库中持久化，支持现有事件补扫、游标重放和服务重启恢复。
- 消息作者、引用作者和 `@` 提及统一显示当前成员名称；历史快照只在当前资料不可用时兜底。
- 旧资料事件不能覆盖更高版本资料；头像被替换或恢复默认时不继续显示旧图片。
- WS 与 REST 只公开聊天室所需的成员标识、名称和资料版本，不公开账号 ID、邮箱、对象存储路径、签名 URL 或头像字节。
- v1 客户端不会因收到未知事件而断开；v2 客户端获得实时资料同步。
- 相关回归测试、两个包的完整质量门通过，或无法执行的外部验收被准确披露。

### Scope

- 服务端资料更新事务与公共事件写入。
- `CommunityEvent` 的增量数据模型和迁移。
- WS v2 的资料更新事件、重放和 v1 兼容投影。
- 受成员权限保护的当前成员资料批量解析接口。
- 客户端成员资料缓存、事件处理和头像版本失效。
- 消息作者、引用、提及及头像的当前资料展示。
- 相邻单元测试、协议测试、隔离数据库测试、聊天室设计文档和验收记录。

### Non-goals

- 不增加公开成员主页、成员列表、好友、私聊、关注或搜索能力。
- 不改变账号资料的编辑入口、头像上传格式、媒体存储供应商或保留策略。
- 不支持客户端主动提交资料广播；公开事件只能由服务端在可信资料更新成功后产生。
- 不为本功能引入 Redis、消息队列、新进程、新依赖或新环境变量。
- 不删除消息中的发送时名称快照，不批量改写历史消息。
- 不宣称支持多实例实时广播；现有公共聊天室仍以单 NestJS 实例为实时通知边界，PostgreSQL 事件负责持久恢复。

### Risks

- 资料更新事务新增公共房间事件序列写入，需要验证与消息发送并发时没有锁顺序死锁。
- 当前 v1 解析器严格拒绝未知事件，必须通过协议协商隔离新事件，不能把新帧直接发给旧客户端。
- 头像事件只能暴露公开可用状态和版本，不能绕过头像公开同意或当前资源生命周期校验。
- 长时间离线或游标过旧时不能依赖实时事件，必须以服务端当前资料重新建立客户端投影。

## 2. 已确认的产品语义

聊天室中的名称和头像表达“这个公共成员现在是谁”，因此正常界面展示当前资料：

| 位置 | 展示规则 |
| --- | --- |
| 消息作者 | 当前名称和当前头像 |
| 历史消息作者 | 当前名称和当前头像 |
| 回复引用作者 | 当前名称 |
| `@` 提及 | 当前名称 |
| 当前资料不可用 | 使用消息、引用或提及内的发送时名称快照兜底 |

消息正文、发送时间、撤回状态和发送时名称快照不随资料变化。资料同步不是编辑消息，也不产生新的聊天消息、未读消息或提及提醒。

## 3. 方案取舍

| 方案 | 收益 | 代价 | 结论 |
| --- | --- | --- | --- |
| 持久化 `MEMBER_PROFILE_UPDATED` 公共事件 | 复用现有序列、补扫、重放和重启恢复；语义与消息事件一致 | 需要增量迁移和协议扩展 | 采用 |
| 仅由 Gateway 进程内广播 | 修改较少、延迟低 | 广播窗口故障和服务重启会丢失，无法重放 | 拒绝 |
| 客户端定时轮询成员资料 | 不扩展 WS 事件 | 有延迟、持续请求、不能达到消息级实时体验 | 拒绝 |

采用服务端权威、持久事件和客户端当前资料投影：消息保留稳定 `memberId` 与历史名称快照，客户端按 `memberId` 解析当前资料。一次成员资料事件更新一份成员投影，不生成或改写数百条历史消息记录。

## 4. 数据模型与事务边界

### 4.1 增量迁移

新增一份 Prisma 迁移，不修改既有迁移：

- `CommunityEventKind` 增加 `MEMBER_PROFILE_UPDATED`。
- `CommunityEvent` 增加仅供该事件使用的公开资料快照字段：
  - `profileName String?`
  - `profileRevision Int?`
  - `profileHasAvatar Boolean?`
- 继续使用现有 `targetMemberId` 表示被更新的公共成员，`actorMemberId` 与目标相同。

选择显式列而不是自由 JSON，便于 Prisma 类型检查、事件投影校验和数据库测试。应用层必须保证 `MEMBER_PROFILE_UPDATED` 的上述字段完整，其他事件不依赖这些字段。迁移只增加枚举值和可空列，不回填、不删除、不覆盖现有用户或聊天数据。

### 4.2 事件写入

新增职责单一的 `CommunityProfileEventWriter`，只依赖 Prisma 和公共聊天室稳定策略，不读取私人书籍、会话、记忆或向量数据。资料模块在自身事务中调用：

1. 仅按固定公共房间和可信 `ownerId` 查询 `CommunityMember`；
2. 已加入时先取得现有公共房间行锁，再锁定并更新当前用户，保持与消息事务一致的锁顺序；
3. 未加入聊天室时只锁定和更新当前用户，不写公共事件；
4. 从更新结果取得服务端生成的当前资料；
5. 已加入时分配下一个连续事件序列，写入目标 `memberId`、规范化名称、更新后的 `profileRevision` 和公开头像可用状态；
6. 资料更新、头像指针变化和公共事件必须一起提交或一起回滚。

Writer 放在不依赖 `UserProfileModule` 的窄模块中，由资料模块和社区模块共同使用，避免 `UserProfileModule` 与 `CommunityModule` 循环依赖。现有 `CommunityService` 的房间锁和序列分配逻辑应抽成共享的内部基础设施，不复制第二套事件序列算法。

以下成功操作写事件：

- 名称实际变化；
- 新头像首次成功确认并成为当前头像；
- 当前头像恢复为默认头像。

以下操作不写事件：

- 只修改或删除壁纸；
- 创建上传票据或上传尚未确认；
- 幂等确认已完成的同一个头像；
- 请求成功但公开资料没有实际变化；
- 用户未加入公共聊天室；
- 事务失败或回滚。

`profileHasAvatar` 只有在当前头像资源属于本人、用途为 `AVATAR`、状态为 `READY` 且成员已同意当前头像公开版本时才为 `true`。客户端提交的资源 ID、owner、memberId 或公开状态不能决定事件内容。

### 4.3 并发与失败

- 对已加入成员，资料事务和消息事务都遵循“公共房间锁 → 用户/成员写入 → 事件序列”的顺序；禁止沿用当前“先锁用户、后锁房间”的调用顺序。
- 增加名称更新、头像确认与消息发送并发的隔离数据库测试，验证序列连续、事务有界且无死锁。
- 事件写入失败必须使本次公开资料变化事务失败；不能返回“资料已同步”但缺少可恢复事件。
- 外部头像读取、解码和规范化仍在进入最终数据库事务前完成；最终头像指针与资料事件在同一短事务中提交。
- 客户端断开不取消已经进入数据库提交阶段的资料事务，但不会导致重复资料事件；幂等头像确认不重复写事件。
- 事务提交后通过进程内 `CommunityEventSignal` 立即唤醒一次现有事件补扫，以满足在线更新延迟目标；即使唤醒失败，1 秒持久补扫定时器和事件重放仍负责恢复。Signal 不携带资料 payload，也不是事件事实源。

## 5. 服务端公开契约

### 5.1 成员资料 DTO

公共成员资料固定为：

```ts
interface CommunityMemberProfile {
  memberId: string;
  name: string;
  profileRevision: string;
  avatarRevision: string | null;
}
```

`profileRevision` 和 `avatarRevision` 使用非负十进制字符串，复用客户端现有安全序列解析边界。存在公开可用头像时，`avatarRevision` 等于当前 `profileRevision`；否则为 `null`。名称由服务端当前 `User.name` 投影，不能接受客户端覆盖。

### 5.2 WS v2 事件

新增持久事件：

```json
{
  "event": "member.profile.updated",
  "data": {
    "seq": "128",
    "member": {
      "memberId": "public-member-id",
      "name": "新名字",
      "profileRevision": "8",
      "avatarRevision": "8"
    }
  }
}
```

恢复默认头像时 `avatarRevision` 为 `null`。该事件：

- 使用公共事件 `seq`，参加严格连续游标、缓冲、补扫和重放；
- 不增加消息未读数、回复未读数或提及未读数；
- 不包含账号 ID、邮箱、资源 ID、对象路径、签名 URL、原头像或操作者原因；
- 相同或更低 `profileRevision` 可安全重复投递，客户端不得回退。

事件服务从持久字段投影，不在重放时读取客户端参数。头像字节仍通过现有受鉴权、受成员关系和公开同意约束的头像接口读取。

### 5.3 协议兼容

新事件不能直接加入严格的 `booksoul.community.v1`。新增 `booksoul.community.v2` 并保留 v1：

- 旧客户端申请票据时不声明版本，继续获得 v1。
- 新客户端申请票据时显式声明 `protocolVersion: 2`，获得绑定 v2 的票据。
- WS 身份记录协商版本，不能由后续帧修改。
- v2 收到完整 `member.profile.updated`。
- v1 对同一持久事件只收到 `{ event: "cursor", data: { seq } }`，从而推进游标但不遇到未知帧。
- 消息、撤回、心跳、presence、错误和恢复语义在两个版本中保持不变。

服务端发布顺序应先支持 v1/v2 双协议，再发布请求 v2 的客户端。回滚到旧服务端时，新客户端应把“不支持 v2”呈现为明确的聊天室版本不兼容，不能静默降级到绕过资料同步的行为。

### 5.4 当前成员资料恢复接口

新增：

```http
POST /api/community/members/resolve
Content-Type: application/json

{ "memberIds": ["member-a", "member-b"] }
```

规则：

- 必须使用 JWT，并先确认调用者是固定公共房间成员。
- `memberIds` 去重后为 1–100 个合法公共成员 ID；拒绝额外字段和账号 ID。
- 查询在固定 `roomId` 和给定公共成员 ID 范围内完成，不按不可信 ID 跨房间读取。
- 只返回存在于当前房间的 `CommunityMemberProfile[]`；未知 ID 不泄露账号信息。
- `Cache-Control: no-store`，请求沿用 10 秒超时和身份代次隔离。

客户端在首次加载一页消息、加载历史、游标过旧 reset 或缓存缺少成员时，收集该页作者、引用和提及的唯一 `memberId`，按上限批量解析。WS 实时事件负责快，解析接口负责最终恢复。

## 6. 客户端状态与渲染

`useCommunityStore` 增加有界当前资料投影：

```ts
memberProfiles: Record<string, CommunityMemberProfile>
```

应用规则：

1. 收到或解析到成员资料时，先验证字段和版本。
2. 缓存不存在或入站 `profileRevision` 更高时替换。
3. 相同版本允许完全相同的幂等重复；冲突内容按协议错误处理，不能任选其一。
4. 更低版本忽略，不能覆盖新名称或头像版本。
5. 账号或 `authGeneration` 变化时与消息、草稿等私人状态一起同步清空。
6. 缓存只保存当前有界消息缓存、窗口、回复目标和提及草稿涉及的成员；消息淘汰后可清理无引用成员，防止无界增长。

展示统一使用：

```ts
memberProfiles[memberId]?.name ?? historicalName
```

适用于消息作者、引用作者和 `@` 提及。WS 事件只更新一份成员投影，React 依赖该投影重新渲染所有相关位置，不遍历并永久改写消息历史快照。

### 6.1 头像失效

`CommunityAvatar` 接收 `memberId` 与 `avatarRevision`，加载键至少包含账号代次、公共成员 ID、头像公开同意版本和头像版本。`avatarRevision` 变化时：

- 取消该组件旧请求；
- 释放旧 Blob URL；
- `avatarRevision !== null` 时立即请求当前头像；
- `avatarRevision === null` 时直接显示由当前名称生成的默认头像；
- 迟到的旧请求不得覆盖新版本。

头像请求可附加仅用于失效和诊断的 `?v=<avatarRevision>`，服务端不能按该值选择资源，仍必须查询当前头像指针并在读取后复核生命周期。响应继续使用 `Cache-Control: no-store`。现有 60 秒头像轮询从正常同步路径移除；若保留可见性恢复请求，只能作为异常自愈，不能成为完成条件。

### 6.2 本地修改者

资料保存 HTTP 响应可立即更新修改者本地的成员投影，减少等待事件补扫的视觉延迟；该更新必须使用服务端返回的 `profileRevision` 和当前聊天室 `memberId`。随后到达的同版本 WS 事件按幂等规则处理。其他用户只依赖服务端广播和恢复接口，不信任修改者客户端转发。

## 7. 恢复、边界与可观测性

- 短暂断线：`connection.resume` 按事件序列重放资料事件。
- 服务重启：现有 `CommunityEventsService` 从数据库水位补扫，不能只依赖进程内回调。
- 游标过旧或慢消费者：沿用 reset，清理旧窗口并获取最新消息、摘要和涉及成员资料。
- 资料事件不改变 `lastReadSeq`、消息计数、在线人数或草稿。
- 日志只记录稳定事件类型、序列、耗时和错误码；不记录名称、头像内容、账号 ID、邮箱、Token 或资源路径。
- 指标可记录资料事件写入/投递/重放数量、投递延迟和资料解析失败码，不记录 payload。
- 头像存储不可用时名称仍更新，头像显示可行动的默认/重试状态；不能退回已经失效的旧头像。

## 8. 实施范围

预期涉及：

- `server/prisma/schema.prisma` 与一份新迁移；
- `server/src/community/` 的事件类型、事件投影、协议协商、票据身份、成员解析和共享事件序列基础设施；
- `server/src/users/profile/` 的名称、头像确认和头像重置事务接入；
- `client/src/lib/community-types.ts`、`community-api.ts`、`community-socket.ts`；
- `client/src/store/useCommunityStore.ts`；
- `client/src/components/CommunityChat/` 的消息、提及、引用和头像展示；
- 相邻单元测试、协议测试和专用隔离数据库测试；
- 现有公共聊天室设计、实施计划或验收记录中被本文替换的资料展示说明。

不新增 npm 依赖，不修改 `.env`、部署端口、媒体供应商、认证方式或私人阅读功能。

## 9. 验收矩阵

| 编号 | 场景 | 通过标准 |
| --- | --- | --- |
| P01 | A、B 已加入并在线；A 修改名称 | A 与 B 在 1.5 秒目标内看到消息作者、引用和提及中的新名称，无刷新或重连 |
| P02 | A 上传并确认新头像 | B 立即请求并显示新头像；旧 Blob URL 释放，迟到旧请求不能回写 |
| P03 | A 恢复默认头像 | A 与 B 移除旧头像并显示由当前名称生成的默认头像 |
| P04 | B 断线后 A 修改资料，B 在重放范围内重连 | B 通过 `member.profile.updated` 重放恢复当前名称和头像版本 |
| P05 | B 游标超过重放范围 | reset 后通过消息快照和 `/members/resolve` 恢复当前资料 |
| P06 | A 连续修改两次，模拟事件乱序或重复应用 | 只显示最高 `profileRevision`；重复事件幂等，旧事件不回退 |
| P07 | A 只修改壁纸、重复确认头像或提交无变化名称 | 不产生 `MEMBER_PROFILE_UPDATED` |
| P08 | 未加入用户修改名称或头像 | 资料正常保存，不创建公共资料事件，不泄露成员存在性 |
| P09 | 资料事务或公共事件写入失败 | 两者一起回滚，不返回部分成功；重试遵循现有 revision 冲突语义 |
| P10 | 资料更新与消息发送并发 | 公共事件序列连续、无重复或空洞、无死锁，消息与资料均可重放 |
| P11 | v1 与 v2 客户端同时连接 | v2 收到资料事件；v1 收到 cursor 且不断开；双方消息功能不回归 |
| P12 | 伪造 resolve ID、跨房间 ID、额外字段或未加入调用 | 请求拒绝或只返回固定房间授权范围；不返回账号 ID、邮箱或媒体路径 |
| P13 | 头像在读取过程中再次被替换 | 服务端读取后复核失败，旧头像不返回；客户端保持新版本或默认状态 |
| P14 | 退出 A 后登录 B，A 的迟到事件/头像请求到达 | A 的资料和 Blob URL 不进入 B 的状态 |
| P15 | 默认 Jest 发现范围与两个包质量门 | 默认测试不连接数据库；客户端、服务端 `npm run check` 通过 |

## 10. 测试与发布验证

### 单元与协议测试

- 资料事件只在公开资料实际变化且用户已加入时创建。
- 名称、头像确认、头像重置及事务回滚路径。
- v1 cursor 投影、v2 完整事件、重放顺序和未知/畸形字段拒绝。
- 成员缓存的版本单调性、幂等、身份代次隔离和有界清理。
- 当前名称覆盖历史快照，以及当前资料缺失时的兜底。
- 头像版本变化、取消、迟到响应、Blob URL 释放和恢复默认头像。
- resolve 接口的成员权限、固定房间作用域、上限与最小返回字段。

### 数据库测试

只通过专用数据库命令运行，并要求显式、隔离且通过门禁的 `TEST_DATABASE_URL`：

- 资料更新与事件同事务提交/回滚；
- 资料更新和消息发送并发序列；
- 断线水位后的资料事件重放；
- 未加入用户不创建事件；
- fixture 仅按本次稳定 ID 清理，禁止全表清空。

若当前环境不能证明测试数据库与实际数据隔离，则不运行数据库测试并准确报告原因。不得修改 `.env`、复用开发库或运行破坏性迁移。

### 双客户端验收

在允许的隔离环境中使用两个账号和两个浏览器上下文：

1. A/B 加入并打开聊天室；
2. A 修改名称，记录保存成功至 B 更新的实际延迟；
3. A 上传新头像并确认，验证 B 的网络请求、画面和旧 Blob 释放；
4. B 断线，A 再次修改，B 重连后验证重放；
5. 触发 reset fixture，验证 resolve 恢复；
6. 保存脱敏步骤和结果，不保存私人头像、邮箱、Token 或完整账号标识。

真实头像验收会写入账号媒体和对象存储，只有在用户明确允许使用指定隔离账号与存储目标后运行；否则使用 mock storage/HTTP/WS harness 验证，并把真实外部验收标为未运行。

## 11. 交付约束

- 先运行最相关的客户端 Vitest 和服务端 Jest，再运行两个包的 `npm run check`。
- 默认测试和质量门必须保持数据库无关；数据库测试发现范围变化时先用只读 listTests 核对。
- 迁移只生成文件，不自动对开发库或生产库执行；实际部署迁移需另行核对数据库目标、备份与恢复路径。
- 交付前检查 diff/status，不包含 `.env`、头像字节、运行时上传、日志、coverage、dist 或无关格式化。
- 若代理、部署顺序或真实 WS 双协议无法本地验证，明确列为发布前验证项，不能声称已通过。
